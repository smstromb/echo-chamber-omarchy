# Feature status

This client implements voice calls, incoming screens, webcams, chat/files, soundboard, device controls and a Jam listener/controller. Full Windows-client parity remains in progress.

**Status key:** Present = implemented; Partial = narrower behavior or incomplete verification; Missing = no usable implementation. Hardware, portal capture and network interoperability need broader testing. The detailed entries identify known gaps rather than imply support from visible controls alone.

Protocol references are pinned to upstream commit `5425b5ba253e031d75bf5e84926e6a9b0f4a74a1`, using active `core/viewer`, `core/control` and registered native-client commands. Archived capture experiments are excluded. See [development](DEVELOPMENT.md) for verification scope.

## What Linux actually limits

**Screen/window video uses the desktop portal.** The implementation uses PipeWire and the Hyprland ScreenCast portal for source selection. Advertised portal capabilities do not establish capture performance; interactive selection, source lifecycle and hardware behavior require verification. [ScreenCast specification][portal]; [Hyprland portal][hypr-portal].

**Outgoing application/system audio needs a different backend.** Electron's `Streams.audio` API documents `loopback`/`loopbackWithMute` as Windows-only. The current code also explicitly disables share audio. PipeWire supports sink monitoring and virtual audio routing, so there is a practical Linux implementation path. Exact application selection, excluding Echo, latency and cleanup remain work to validate. [PipeWire loopback][pipewire]; local Electron type declaration `node_modules/electron/electron.d.ts` (`interface Streams`).

**Windows capture/graphics optimizations cannot be copied verbatim.** WGC/DXGI/D3D11/WASAPI and the current native presenter are Windows APIs. Capture a game as a portal window/monitor first. Separate benchmarks must establish whether the Linux path meets the required resolution, FPS, latency, colors and resource use; minimized/protected surfaces and compositor behavior need explicit tests. Neither “Linux cannot screen-share” nor “identical Windows performance is already available” is justified.

**No OS obstacle was identified for the ordinary protocol/UI features:** chat, files, profiles, soundboard, chimes, device selectors, independent audio mix, camera, screen viewing controls, existing-Jam listening/control, dashboards and diagnostics. Many are now implemented; see the current statuses above. Remaining gaps are client implementation work. Jam source hosting and capture-performance parity are larger Linux integrations.

## Remaining acceptance criteria

These acceptance criteria define the remaining compatibility and reliability work. The status tables distinguish implemented functionality from gaps.

1. **Protocol and session foundation.** Extract testable room/media/auth services from the current controller; add typed data-message routing, TURN configuration, track/source normalization, identity mapping and capability/version checks. Preserve the old room on failed switches and ignore stale asynchronous events. Acceptance: Windows and Linux coexist through late joins, room switches, network loss and reconnect without phantom people or resurrected media.
2. **Core call parity.** Device settings, independent 0–300% voice/screen gain, chime gain, RNNoise controls, webcam, local preview, correct camera/screen tiles and unified output mute. Acceptance: hot-plug devices and change outputs while connected; every mute and gain control changes only its documented bus and persists appropriately.
3. **Screen-sharing parity.** Complete portal selection/cancel/stop, source lifecycle, per-stream viewing and fullscreen; add compatible source/activity/bitrate messages and diagnostic metrics. Implement outgoing PipeWire application/system audio with Echo exclusion. Acceptance: actual Windows-to-Linux and Linux-to-Windows video+audio; no self-echo; correct handling of source close, resize, restart, hidden views and multiple shares.
4. **Communication features.** Chat/history/deletion, files and clipboard images, avatars/device profiles, soundboard, chimes and PG-13 state. Acceptance: mixed-client room tests for every message type and persisted operation, including duplicates, reconnect and room isolation.
5. **Jam listener/controller parity.** Current protocol-v3 membership/audio, account/library flows, search/favorites/history, idempotent queue operations and distinct playback/teardown actions. Acceptance: Linux listens to the existing Windows source; reconnect does not duplicate queue entries, leak membership or restore stale playback.
6. **Administrative/desktop completion.** Dashboard/authorized moderation, opt-in diagnostics/reporting, Linux packaging/update/migration, settings and window behavior. Acceptance: clean install/update/removal plus safe credential and preference migration; no Windows installer assumptions.
7. **Optional native performance/source work.** Linux Spotify source and a native capture/presenter path only where benchmarked requirements justify it. These are separable from full ordinary participant feature parity.

Feature completeness should be tracked by these capabilities and mixed-client acceptance tests, not by copying the Windows layout or by a percentage based on counting buttons. This audit does not claim implementation of the missing rows.
