# Echo Chamber Linux feature parity audit

Date: 2026-09-05. Target: full user-facing functionality with an independent Linux UI and Omarchy toolbar.

The Linux client now implements core calls plus real chat/files, soundboard, webcams, device controls, profiles, shared PG-13 state, and a protocol-v3 Jam listener/controller. It is still **not feature complete**. The explicit design preview remains synthetic; the same controls in the desktop client now have real integrations. The largest missing platform work is outgoing application/system audio, capture optimization and hosting the Spotify audio source. Ordinary screen/window video has a portal implementation, but interactive capture on this machine still needs verification.

## Implementation pass — 2026-09-05

Added a room-data service with sender/room/generation checks, duplicate handling and deletion-safe history merging; authenticated media operations stay in the main process. Chat supports history, sending/deleting own messages, file uploads, clipboard files/images, inline raster/audio/video preview, explicit downloads, external web links, emoji and unread state. The toolbar receives only call state, not chat history or credentials.

Added webcam publishing/local preview; persistent input/output/camera selectors with device refresh and unplug fallback; browser noise-suppression toggle; Web Audio amplification to 300%; shared output mute for calls, Jam and effects; avatar upload/display/device announcements; built-in and custom chimes; soundboard playback/upload/edit/favourites/search; PG-13 state; and stream-description reception. Profile hardware/server interoperability and soundboard upload remain less tested than the core flows.

Jam supports current source status, authenticated PCM streaming, start/join/leave, track search, queue add/remove, skip, Stop Music, End Jam and independent volume. It checks protocol/source readiness, fences generations and reconnects while listening. Adding a track reuses a request ID for an interrupted response during the current app session. Spotify OAuth, playlist/library/favourites/history workflows, durable retry IDs, visualizer and Linux source hosting remain missing.

Connection improvements include authenticated ICE configuration with a visible fallback error, superseded/cancellable joins, stale-room event rejection, explicit sign-out/forget. Safe room-switch rollback remains missing. Hiding incoming video now calls LiveKit's receive-disable control; audio remains independent, and video intent is reapplied to replacement tracks during that call.

Password persistence now explicitly selects Omarchy's GNOME libsecret backend, respecting command-line overrides. Session credentials and saved credentials are separate; a renderer reload does not enable saving. Sign-in commits connection and encrypted credentials only after authentication succeeds, with atomic file replacement. A real-keyring isolated test verifies full-process restart/automatic sign-in, failed-login preservation, explicit forget, and memory-only reload/restart behavior. Plaintext-backend saving remains disabled. Existing running processes need a full restart to acquire the backend fix; memory-only users must enter the password again.

Verification: unit/protocol regressions, isolated Electron desktop flows, and a real loopback LiveKit SFU plus an Echo API/Jam WebSocket fixture. Integration checks cover received audio/video, real microphone and fake-camera publication, local preview removal, 170% gain, chat send/receive/delete, uploaded attachment decoding, sound playback/edit events, PG-13, Jam authentication/PCM/search/queue/stop/end, device settings and leave cleanup. These are **not** a real Windows deployment, real webcam/microphone hardware, WAN/TURN, Spotify or interactive screen-capture test.

## Existing-stream join regression

A live call exposed a renderer race: tracks subscribed during `joining` were attached, then the next render cleared the media registry because the call was not yet marked `joined`. Audio elements survived, so existing screen shares could be heard but not viewed. The local SFU test now publishes the remote stream **before** Linux joins and delays audio startup to exercise this boundary. The previous renderer fails with no video elements; the corrected renderer passes the complete flow. Tracks survive joining/reconnecting and clear only on a real leave. Known shares without video show a connecting/retry tile; private status now includes publication state and received dimensions for diagnosis.

## What Linux actually limits

**Screen/window video is supported.** This machine has PipeWire 1.6.8, WirePlumber 0.5.15, xdg-desktop-portal 1.22.1 and the Hyprland portal 1.4.1. The live ScreenCast `AvailableSourceTypes` value was **7**, advertising monitor, window and virtual sources. That verifies advertised capability, not a successful capture or a particular FPS. Use the consent-based portal. [ScreenCast specification][portal]; [Hyprland portal][hypr-portal].

**Outgoing application/system audio needs a different backend.** Electron's installed `Streams.audio` API documents `loopback`/`loopbackWithMute` as Windows-only. The current code also explicitly disables share audio. PipeWire supports sink monitoring and virtual audio routing, so there is a practical Linux implementation path. Exact application selection, excluding Echo, latency and cleanup remain work to validate. [PipeWire loopback][pipewire]; local Electron type declaration `node_modules/electron/electron.d.ts` (`interface Streams`).

**Windows capture/graphics optimizations cannot be copied verbatim.** WGC/DXGI/D3D11/WASAPI and the current native presenter are Windows APIs. Capture a game as a portal window/monitor first. Separate benchmarks must establish whether the Linux path meets the required resolution, FPS, latency, colors and resource use; minimized/protected surfaces and compositor behavior need explicit tests. Neither “Linux cannot screen-share” nor “identical Windows performance is already available” is justified.

**No OS obstacle was identified for the ordinary protocol/UI features:** chat, files, profiles, soundboard, chimes, device selectors, independent audio mix, camera, screen viewing controls, existing-Jam listening/control, dashboards and diagnostics. Many are now implemented; see the current statuses above. Remaining gaps are client implementation work. Jam source hosting and capture-performance parity are larger Linux integrations.

## Original implementation sequence and acceptance criteria

This sequence records the full target. Several parts are now complete; use the status tables and implementation-pass notes above for remaining work.

1. **Protocol and session foundation.** Extract testable room/media/auth services from the current controller; add typed data-message routing, TURN configuration, track/source normalization, identity mapping and capability/version checks. Preserve the old room on failed switches and ignore stale asynchronous events. Acceptance: Windows and Linux coexist through late joins, room switches, network loss and reconnect without phantom people or resurrected media.
2. **Core call parity.** Device settings, independent 0–300% voice/screen gain, chime gain, RNNoise controls, webcam, local preview, correct camera/screen tiles and unified output mute. Acceptance: hot-plug devices and change outputs while connected; every mute and gain control changes only its documented bus and persists appropriately.
3. **Screen-sharing parity.** Complete portal selection/cancel/stop, source lifecycle, per-stream viewing and fullscreen; add compatible source/activity/bitrate messages and diagnostic metrics. Implement outgoing PipeWire application/system audio with Echo exclusion. Acceptance: actual Windows-to-Linux and Linux-to-Windows video+audio; no self-echo; correct handling of source close, resize, restart, hidden views and multiple shares.
4. **Communication features.** Chat/history/deletion, files and clipboard images, avatars/device profiles, soundboard, chimes and PG-13 state. Acceptance: mixed-client room tests for every message type and persisted operation, including duplicates, reconnect and room isolation.
5. **Jam listener/controller parity.** Current protocol-v3 membership/audio, account/library flows, search/favorites/history, idempotent queue operations and distinct playback/teardown actions. Acceptance: Linux listens to the existing Windows source; reconnect does not duplicate queue entries, leak membership or restore stale playback.
6. **Administrative/desktop completion.** Dashboard/authorized moderation, opt-in diagnostics/reporting, Linux packaging/update/migration, settings and window behavior. Acceptance: clean install/update/removal plus safe credential and preference migration; no Windows installer assumptions.
7. **Optional native performance/source work.** Linux Spotify source and a native capture/presenter path only where benchmarked requirements justify it. These are separable from full ordinary participant feature parity.

Feature completeness should be tracked by these capabilities and mixed-client acceptance tests, not by copying the Windows layout or by a percentage based on counting buttons. This audit does not claim implementation of the missing rows.
